# exam-proctor-client 修改方向（未修改客户端代码）

OJ 端协议详见 [proctor-protocol.md](./proctor-protocol.md)。以下是基于当前客户端源码的改造建议，不代表已实现客户端功能。

## 当前实现的差距

- `app/main/audit-logger.js` 每次启动新建明文 `.log` 和 `.json`，没有加密、同一次考试续写或上传确认。
- `app/main/index.js` 目前启动网络/防作弊保护并载入 targetUrl，没有自动设备签名握手、互相验签、令牌刷新或结束上传事务。
- `app/preload/preload.js` 只暴露 ping/requestQuit，缺少受限的 `examAPI.proctorHeaders`。悬浮计时从每次页面挂载开始，也不是服务端 attempt 生命周期。
- `config/exam-config.json`、`version.json` 目前提供 URL/版本/热更新配置，但不含服务端信任锚、协议版本、比赛身份或可信更新签名。

## 建议改造模块

### 1. 认证与设备身份（新增主进程模块）

- 新增 `proctor-auth.js`，使用 Node crypto 的 Ed25519、规范化 JSON、SHA-256 和安全随机数，严格实现 OJ 协议。
- 为安装设备生成独立密钥；Windows 使用受当前账号/设备保护的存储（例如适当使用 Electron safeStorage/DPAPI）。不能把所有安装包共用的私钥写死在 asar 中，不能把私钥交给 renderer。
- 在打包前增加构建脚本，从 `PROCTOR_AUTH_PUBLIC_KEY`、`PROCTOR_LOG_PUBLIC_KEY`、`PROCTOR_KEY_ID` 读取同次生成的认证公钥、日志加密公钥和密钥 ID，验证 Ed25519 / RSA-3072 公钥类型及 keyId 格式，生成供主进程读取的信任配置；缺失或不合法必须终止构建。该生成文件应被 gitignore 排除。现有 `pack` / `dist` / `release:hot` 均应调用该校验，不只修改一个打包入口。
- 变量由本地构建环境或 CI 注入，不在公开源码中写真实值；保留 PEM 的换行。公钥可从分发包中提取，这是正常现象，不能依赖隐藏公钥认证官方客户端。两组服务端私钥永不进入构建变量/asar/热更新包；设备私钥由安装后的主进程单独生成并保护。
- 使用构建时认证公钥验签服务端，使用日志加密公钥包装最终日志 AES 密钥，分别使用，不能互换。记录目标 HTTPS origin；支持受信版本更新时轮换信任锚，不能从普通网页静默信任新公钥。
- 删除注册码、人工设备登记及首次注册 UI。登录且报名的用户自动 challenge → 验证服务端签名 → 用设备私钥签同一挑战 → handshake → 验证令牌签名 → 接受令牌。请求使用 Electron 会话的 Hydro Cookie，避免拿到另一用户的 Cookie。
- challenge 的 `deviceInfo` 仅包含 platform / osVersion / arch，每项最多 128 字符；不要上传主机名、完整硬件清单或其它不必要个人信息。不要在请求体自报 IP，服务端自行记录。首次生成的设备密钥在同次比赛重启后继续使用。
- 版本从受信安装元数据读取；环境指纹由主进程确定稳定字段后 SHA-256，不收集多余隐私。指纹在一次 attempt 内不得变化。主动支持自报版本无法证明二进制完整性的限制，不声称能阻止所有篡改。
- 验证服务端挑战全部字段与签名，再签同一 transcript；接受令牌前验证服务端会话签名。主进程保管令牌，过期前单飞刷新；异常恢复时重新握手，禁止并发刷新导致乱序令牌覆盖。

### 2. preload / IPC 接口

- `preload.js` 暴露规范中的 `proctorHeaders({action,method,path,payload})`，通过严格验证后的 IPC 调用主进程；保留 contextIsolation，renderer 不可访问 Node。
- IPC 校验发送者窗口/frame、HTTPS origin、域、比赛、合法提交 path、payload 类型/长度；不提供通用签名任意文本的接口，不暴露完整会话存储。
- 文件提交入口应按文件字节求摘要，再取得相同的签名头；网络请求拦截如用于补充认证，需要正确处理 JSON/multipart，不能仅检查 User-Agent 或注入静态令牌。
- OJ 的 ui-next 已调用这个桥；返回小写 `x-proctor-token` 和 `x-proctor-proof` 两个头。非监考比赛无需该桥。

### 3. 本地实时加密日志与恢复

- 不再使用现有明文双文件。按 attemptId 保存一个可恢复的本地状态目录；保存绑定 UID、域、比赛、设备 ID、创建时间、日志序号、上次已持久化记录，以及 clean-shutdown 标记。
- 每条事件序列化后使用独立 nonce 的 AEAD 加密落盘，采用追加式 journal；落盘完成后才递增已持久化序号。切勿每次更新重写整个历史数组，避免异常退出损坏全部日志。
- 每条包含递增序号、UTC 时间、单调时钟时间、事件类型；建议加前条记录摘要形成链，记录客户端启动、握手、刷新、失焦、黑名单、网络保护、提交、自测、结束操作。摘要链有助于检查损坏，但不等同于可信远程证明。
- 启动检测同一未完成 attempt：若上次没有正常退出标记，追加 `ABNORMAL_EXIT_DETECTED`；追加 `CLIENT_RESTART`（确认系统确实重启时再记录 `SYSTEM_RESTART`，可比较稳定 boot 标识，不能把所有进程重启都称作系统重启）。恢复最后完整且验证通过的加密记录，损坏尾部必须另记事件，不能静默丢弃。
- 密钥、nonce 计数器、日志及状态应采用安全/原子持久化；每个加密 nonce 只能用一次。断电恢复不能回退 nonce 后复用。

### 4. 结束监考与补传队列

- 用户点击现有 requestQuit，先停发新提交、等在途提交响应，再调用 finish；进入不可继续考试的 closing 状态。保留现有紧急安全退出和系统恢复，不能因网络故障把用户无限锁在 kiosk/防火墙中。
- 验证本地 journal 全部记录后生成最终 `.hplog`：新的 AES-256-GCM 密钥/IV、规定 AAD、RSA-OAEP-SHA256 包装、正确 header 和 ciphertext。最终文件生成后原子标为 pending-upload，禁止以后覆盖/追加该文件。
- 用完整文件摘要和文件大小生成 upload proof，multipart 上传。成功响应或 status 查询确认 receipt 后标为 uploaded。保留回执；无需上传实时日志。
- 失败时明确提示“成绩待确认，日志未上传”，把加密文件放入持久化补传队列；网络恢复/重启自动按有限退避重试，先更新/恢复认证。过期 version 等永久错误提示人工处理，不无限重试。
- 重启需要续写的是尚未 finish 的 journal；已结束但未上传的是固定最终文件，只能补传，不得恢复答题或把不同 attempt 的日志混合。成功上传后才允许清理本地日志，按隐私策略保留回执即可。

### 5. 可信更新与发布

- 现有 updater 不应只依赖可修改的 version.json 和下载 SHA-256。给更新 manifest/安装包签名，客户端先验证可信发布签名再加载 asar；HTTPS 和摘要不能替代发布者身份验证。
- OJ 要求精确版本，先发布可支持协议的客户端和信任锚，再在 OJ 设置相同版本，最后启用比赛监考。考试期间禁止中途热更新导致密钥/指纹/版本突变。
- 本地/远程系统权限与锁屏不是不可绕过的安全边界；Windows 管理员可以干预进程。若需要更强保证，另外评估代码签名验证、TPM 设备凭据或可信启动证明。

## 客户端验收清单

- Windows 正常退出、任务管理器强退、断电、系统重启后日志连续且事件正确。
- 每次提交与自测验签正确；代码/域/比赛改变、proof 重放、旧版本、撤销会话均拒绝。
- 刷新仅一个在途任务；401/403 不能无限显示“等待”。
- 网络中断后可安全退出，之后补传成功；响应丢失不会重开考试，网络 IP 变化不阻止相同设备重新握手。
- 构建缺少任一公钥或 keyId 时失败；两组公钥与后台匹配；私钥不出现在分发包中。
- 不把设备私钥、会话令牌写入 renderer、console、错误堆栈或日志。
- 覆盖主域、子域、代理 HTTPS、公钥轮换、多用户切换、服务端重启和日志批量下载/离线解密。
