- 在插件全部成功启用的前提下，原有数据位置、主域/子域 URL、主要业务权限和核心算法保留，未发现本次拆分新增的普通用户提权路径。

## 尚需注意的问题

以下保留审查时的问题与证据，修复状态见本文末尾“后续处理”。

### P2：前端插件脚本的共同故障影响面扩大

ui-next 原本就使用统一插件入口；现在更多原有功能迁入该入口。因此这不是本次新写出的加载器缺陷，但故障影响面明显扩大：

- 生产环境 `plugins.js` 加载失败时只输出控制台警告，主界面仍继续启动，但插件功能不注册。用户可能误以为回放、粘贴策略、公告等仍在正常工作。
- 开发环境的 `virtual:hydro-plugins` 导入没有同样的错误兜底；导入失败会阻止 `createRoot()` 执行。
- 各插件 `setup()` 的单独异常有捕获，组件也有错误边界；不能把它描述为“任意组件错误都导致全部插件失效”。风险主要在共同入口的导入/构建阶段。

证据：`packages/ui-next/src/main.tsx:28`、`packages/ui-next/index.ts` 中的 `buildPlugins()`。

建议：增加可见的插件健康提示、对关键插件校验就绪状态，并评估独立入口与失败隔离；监考仍应保持后端拒绝策略。

### P2：配置中存在插件不代表后端一定成功启用

`global.addons` 在预加载阶段填充；前端发现函数按路径检查 `ui/index.*`，没有核对后端初始化成功状态。个别插件后端初始化失败后，仍可能出现前端页面/菜单而接口缺失的情况。

证据：`packages/hydrooj/src/loader.ts` 的 `preload()`、`packages/hydrooj/src/entry/common.ts`、`packages/ui-next/index.ts:49`。

本次私信入口要求后端明确下发 `privateMessagesEntryVisible === true` 才出现，避免为这一新入口增加悬空链接；其它插件尚未统一增加这种就绪标记。

### P2：扩展接口并非完全兼容

- `RecordModel.getUserContributions()` 不再存在；实现位于 `packages/user-contributions/model.ts`。
- `@hydrooj/common` 不再导出旧贡献图类型，类型移至 `packages/user-contributions/types.ts`。
- 原核心/前端私有监考、头像框、更新等文件路径移除。使用旧内部路径的外部脚本或 addon 需要调整。
- `getRecordAccess().proctorSession` 虽保留字段名，但返回的是不透明授权对象，不是原 Session 结构。旧调用若读取 `.uid`、`.expiresAt` 等内部字段，仍不兼容，应使用 `accessGrant.assert()`。
- 当前仓库内调用已适配；没有访问用户部署中的第三方插件，不能保证外部调用全部兼容。

新增事件、插槽依赖本仓库配套核心，不能只凭 peerDependencies 中的 Hydro 版本范围就断定插件可无修改安装到上游原版。

### P3：头像框索引初始化重复

`packages/honor-frame/model.ts` 仍导出 `apply()`，Hydro 会在 model 阶段自动调用；随后 `packages/honor-frame/index.ts:6` 又直接调用同一初始化函数。隔离启动日志中也能看到 model 和 index 两个加载阶段。

当前操作主要是幂等索引创建，没有发现重复注册业务路由、数据重复授予或权限变化，但会增加启动数据库请求。建议改为与更新中心/监考一致的单一初始化入口。

## 不是迁移新增，但必须说明的安全边界

1. 头像框管理拥有 `PRIV_EDIT_SYSTEM` 检查，但其处理器没有额外 `requireSudo`。基线也一样，不能称作“迁移丢失了 sudo”，也不能像旧说明那样宣称已经受管理模式保护。本次纠正了说明，未擅自改动其认证流程。
2. 私信仍是全站账户间的消息，不按域隔离；当前域只影响名称展示。隐藏入口不等于禁用私信，停用私信 UI 插件也不会删除核心系统通知与订阅能力。
3. 粘贴限制可被修改浏览器代码或直接请求绕开，这在基线中已存在。计时的前台活动信号也不是可信硬件证明。
4. 监考公钥不是秘密，现有握手不能证明用户使用未经修改的官方安装包。新增日志身份头校验也不等于事件内容真实性审计。

## 本次恢复私信入口的行为

- 桌面：topbar 个人下拉栏的“消息”。移动端：个人菜单对应入口，点击后关闭抽屉。
- 管理员：`/manage/setting` → 基本设置 → “显示私信入口”。键名 `private-messages.showEntry`，默认开启，保存于服务端，全站生效。
- 关闭后只隐藏入口，直接访问 `/home/messages` 及域内地址仍按原权限工作。保存后刷新或下次页面导航读取最新设置；不向已打开的其它浏览器窗口实时广播 UI 状态。
- 未登录不显示；后端未成功注册该功能时不显示。
- 通过公共 `AccountMenuExtras` 插槽接入，topbar 未硬编码私信实现。

## 后续处理（2026-10-26）

按“修复影响较大的问题，暂不调整轻微问题”的要求处理：

- **共同加载故障：已修复。** 生产环境逐个编译插件，开发/生产环境均逐个导入，保留配置中的安装顺序。单个编译、导入、初始化异常不会中断其它插件；入口与单插件异步加载有超时兜底，主界面仍可启动。页面会显示不可用插件及刷新按钮，不再仅在控制台提示。
- **后端初始化失败仍暴露前端：已修复。** 前端发现同时检查启动失败记录和已创建的插件运行状态；失败的插件不进入前端构建或导入，统一显示不可用提示。纯前端插件不要求存在后端入口。
- 资源发布仍在编译完成后统一切换，保留 CSS 注入、二进制资源及分块；只清理旧插件资源，不清理语言、版本、编程语言等核心常量。入口带内容版本参数，避免修改样式后仍命中旧插件缓存。
- **粘贴上限：新增管理员配置。** 默认 30；取消复选框对应 -1（不限），0 禁止粘贴，正整数限制单次 Unicode 码点数。后端在保存前拒绝非法值，原权限豁免保留。它依旧不是服务端防作弊边界。
- **旧私有接口兼容：未恢复。** 仓库内调用已经适配，没有第三方调用故障证据；未重新公开监考会话内部结构或恢复旧私有模块路径。
- **头像框重复索引初始化：暂不改动。** 当前属于幂等操作，未发现功能或权限损失。

故障隔离不表示热停用或自动重试：管理员修复插件后需刷新页面；已经执行了一部分初始化后抛错的插件，不保证能自动撤销所有第三方副作用。监考的后端拒绝策略不变。
